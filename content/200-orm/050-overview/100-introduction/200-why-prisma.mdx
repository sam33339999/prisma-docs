在本頁面中，您將了解 Prisma ORM 的動機，以及它與其他資料庫工具（如傳統 ORM 和 SQL 查詢建構器）的比較。

使用關聯式資料庫是應用程式開發的主要瓶頸。除錯 SQL 查詢或複雜的 ORM 物件經常會消耗數小時的開發時間。

Prisma ORM 透過提供乾淨且型別安全的 API 來提交資料庫查詢，使開發者能夠輕鬆理解他們的資料庫查詢，並回傳 _純 JavaScript 物件_。

## 摘要

Prisma ORM 的主要目標是讓應用程式開發者在處理資料庫時更有生產力。以下是 Prisma ORM 如何實現這一目標的一些範例：

- **以物件思考** 而不是對應關聯式資料
- **查詢而非類別** 以避免複雜的模型物件
- **單一事實來源** 用於資料庫和應用程式模型
- **健康的限制** 防止常見陷阱和反模式
- **讓正確的事情變得容易的抽象** （「成功之坑」）
- **型別安全的資料庫查詢** 可在編譯時驗證
- **更少的樣板程式碼** 讓開發者可以專注於應用程式的重要部分
- **程式碼編輯器中的自動完成** 而不需要查閱文件

本頁面的其餘部分討論 Prisma ORM 與現有資料庫工具的比較。

## SQL、傳統 ORM 和其他資料庫工具的問題

目前存在於 Node.js 和 TypeScript 生態系統中的資料庫工具的主要問題是，它們需要在 _生產力_ 和 _控制力_ 之間進行重大權衡。

![ORM、SQL 查詢建構器和 SQL 中的生產力與控制力](./node-js-db-tools-tradeoffs.png)

### 原始 SQL：完全控制，低生產力

使用原始 SQL（例如使用原生的 [`pg`](https://node-postgres.com/) 或 [`mysql`](https://github.com/mysqljs/mysql) Node.js 資料庫驅動程式），您可以完全控制資料庫操作。然而，生產力會受到影響，因為向資料庫傳送純 SQL 字串很繁瑣，並且伴隨著大量開銷（手動連接處理、重複的樣板程式碼等）。

這種方法的另一個主要問題是，您的查詢結果不會獲得任何型別安全。當然，您可以手動為結果加上型別，但這需要大量工作，並且每次變更資料庫 schema 或查詢時都需要進行重大重構以保持型別同步。

此外，以純字串提交 SQL 查詢意味著您在編輯器中不會獲得任何自動完成。

### SQL 查詢建構器：高控制力，中等生產力

一個常見的解決方案是使用 SQL 查詢建構器（例如 [knex.js](https://knexjs.org/)），它保留了高度的控制力並提供更好的生產力。這類工具提供程式化的抽象來構建 SQL 查詢。

SQL 查詢建構器最大的缺點是，應用程式開發者仍然需要以 SQL 的角度思考他們的資料。這會產生將關聯式資料轉換為物件的認知和實際成本。另一個問題是，如果您不確切知道在 SQL 查詢中在做什麼，很容易搬石頭砸自己的腳。

### 傳統 ORM：較少控制，更好的生產力

傳統 ORM 透過讓您 _將應用程式模型定義為類別_ 來抽象化 SQL，這些類別被對應到資料庫中的表格。

> 「物件關聯對應器」（ORM）的存在是為了彌合程式設計師的朋友（物件）和資料庫的原始型態（關聯）之間的差距。這些不同模型的原因既有文化上的也有功能上的：程式設計師喜歡物件，因為它們封裝了執行中程式單一事物的狀態。資料庫喜歡關聯，因為它們更適合整個資料集的約束和有效的存取模式。
>
> [The Troublesome Active Record Pattern, Cal Paterson (2020)](https://calpaterson.com/activerecord.html)

然後您可以透過呼叫模型類別實例上的方法來讀取和寫入資料。

這要方便得多，並且更接近開發者思考資料時的心智模型。那麼，問題在哪裡呢？

> ORM 代表了一個泥淖，它開始得很好，隨著時間的推移變得更加複雜，不久之後就讓使用者陷入一個沒有明確界限、沒有明確勝利條件、也沒有明確退出策略的承諾中。
>
> [The Vietnam of Computer Science, Ted Neward (2006)](https://blog.codinghorror.com/object-relational-mapping-is-the-vietnam-of-computer-science/)

作為應用程式開發者，您對資料的心智模型是 _物件_。另一方面，SQL 中資料的心智模型是 _表格_。

這兩種不同資料表示之間的差異通常被稱為[物件關聯阻抗不匹配](https://en.wikipedia.org/wiki/Object-relational_impedance_mismatch)。物件關聯阻抗不匹配也是許多開發者不喜歡使用傳統 ORM 的主要原因。

舉例來說，考慮每種方法如何組織資料和處理關聯：

- **關聯式資料庫**：資料通常是正規化的（扁平的），並使用外鍵來連結實體。然後需要 JOIN 實體來顯現實際的關聯。
- **物件導向**：物件可以是深度巢狀的結構，您可以透過使用點記法來遍歷關聯。

這暗示了傳統 ORM 的一個主要陷阱：雖然它們讓您 _看起來_ 可以簡單地使用熟悉的點記法來遍歷關聯，但在底層，ORM 會生成 SQL JOIN，這些 JOIN 是昂貴的，並且有可能大幅降低應用程式的速度（其中一個症狀是 [n+1 問題](https://stackoverflow.com/questions/97197/what-is-the-n1-selects-problem-in-orm-object-relational-mapping)）。

總結：傳統 ORM 的吸引力在於抽象化關聯式模型，並純粹以物件的角度思考資料。雖然這個前提很棒，但它基於錯誤的假設，即關聯式資料可以輕鬆對應到物件，這導致了許多複雜性和陷阱。

## 應用程式開發者應該關心資料 - 而非 SQL

儘管 SQL 是在 1970 年代開發的（！），但它以令人印象深刻的方式經受住了時間的考驗。然而，隨著開發者工具的進步和現代化，值得問的是，SQL 真的是應用程式開發者最好的抽象嗎？

畢竟，**開發者應該只關心實現功能所需的 _資料_**，而不是花時間弄清楚複雜的 SQL 查詢或調整查詢結果以符合他們的需求。

關於在應用程式開發中使用 SQL 還有另一個論點。如果您確切知道自己在做什麼，SQL 的強大功能可能是一種祝福，但它的複雜性可能是一種詛咒。有很多[反模式](https://www.slideshare.net/billkarwin/sql-antipatterns-strike-back)和陷阱，即使是經驗豐富的 SQL 使用者也難以預料，通常以效能和數小時的除錯時間為代價。

開發者應該能夠請求他們需要的資料，而不必擔心在 SQL 查詢中「做正確的事」。他們應該使用為他們做出正確決策的抽象。這可能意味著抽象施加某些「健康」的限制，以防止開發者犯錯。
